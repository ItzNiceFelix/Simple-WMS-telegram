## Trace of the two inputs feeding the deterministic doc id

`id_movement = "sync_" + draft.id + "_" + item.kode_barang` (`syncStokDuaArah.js:510`, `:596`).

- `draft.id` - generated by Firestore `db.collection("sync_stok_drafts").add(...)` (`:210`), then read back via `ambilDraftByIds` (`:447-454`). Firestore-generated, opaque, always a valid doc id. Not user-controllable. SAFE.
- `item.kode_barang` - originates from `products` document ids. It is written by `simpanProduk(kodeBarang, ...)` / `updateProduk` in `lib/models/produk.js:77-96`, keyed by `db.collection("products").doc(kodeBarang)`.
  - Upstream origin is user/LLM input: `chatHandler.js:736-762` takes `kodeBarang` from the `tambahProdukBaru` tool args, trims it, and passes it to `simpanProduk`. Batch path `chatHandler.js:874-883` parses `kodeBarang` from admin text. Validation is `.trim()` only - no charset/format allowlist.
  - **However**: for a code to exist as a `products` doc id at all, it must already have passed through `db.collection("products").doc(kode)` in a prior successful write. Firestore rejects document ids containing `/`, and rejects `.`/`..` as full ids. So any `kode_barang` reachable at sync time is already a syntactically valid Firestore doc id.
  - Consequence for the movement id: Firestore does NOT treat a `/` in `.doc(id)` as a path segment - it rejects the id outright. There is no path traversal into another collection. Worst case from a malformed code is a thrown write error, not a cross-collection write.

## Findings

### MAJOR-1 - Formula / CSV injection via `USER_ENTERED` on user-controlled product fields

Location:
- `lib/sheets/client.js:172` (`tambahBarisBaru` → `valueInputOption: "USER_ENTERED"`)
- `lib/sheets/client.js:84` (`tulisRange` → `valueInputOption: "USER_ENTERED"`)
- Written values: `lib/sheets/syncStokDuaArah.js:563-566` (`row[1] = item.kode_barang`, `row[2] = item.nama_accurate`, plus hpp/nilai)

`kode_barang` and `nama_accurate` are user/LLM-controlled (see trace above). `applyDraftProdukBaru` inserts them into a spreadsheet cell with `USER_ENTERED`. A value beginning with `=`, `+`, `-`, or `@` is interpreted by Google Sheets as a formula. `nama_accurate` is free text (no charset restriction anywhere in `simpanProduk`/`handleTambahProdukBaru`). This is a classic spreadsheet formula/CSV-injection sink: an admin-registered product name or code can exfiltrate neighbouring sheet cells (e.g. via `=IMPORTXML(...)` / `HYPERLINK`) or execute on any downstream export.

Mitigating context:
- The `USER_ENTERED` option itself is pre-existing (`client.js` has used it since the initial Sheets client), so the option is not introduced by this diff.
- What is new/introduced here is the PRODUK_BARU insert path (`tambahBarisBaru`) writing arbitrary user text into cells, and the deterministic-id change does not alter this.
- Impact is confined to the private operational spreadsheet the bot already owns; not an external-user surface. But the product fields are attacker-influenced through the chat registration flow.

Recommendation: prefix-escape untrusted strings (leading `'` or set `RAW` value-input for the text columns), or validate `kode_barang` with a strict charset regex at registration (`simpanProduk`). Smaller, more correct fix: validate at the boundary (`simpanProduk`) - "shortest working diff" is a regex there, not in the sheets layer.

### MINOR-1 - Error log may echo Sheets identifiers / range

Location: `lib/sheets/syncStokDuaArah.js:556`
`console.error("[sync_stok_produk_baru] bacaRange A2:A gagal, fallback nomor:", String(e))` logs the raw caught error. Google Sheets API errors routinely embed the spreadsheet id and A1 range. Spreadsheet id is a semi-sensitive identifier (not a credential, but stable and non-public). No token/key/private-key material is logged. Low practical risk (server logs only). Recommend logging a fixed message + error code, not the raw `String(e)`.

### MINOR-2 - Column-A range read failure silently degrades to empty No

Location: `lib/sheets/syncStokDuaArah.js:551-558`
On `bacaRange` failure the fallback sets `nomor = ""` (empty) rather than aborting the insert. Behaviour: the new row is still appended with a blank No column. This is deliberate ("Gagal baca JANGAN menggagalkan insert") and the No is cosmetic, so not a security defect - flagged only because a silent partial failure can mask a broader Sheets outage (e.g. auth/permission failure), which the operator would want surfaced. INFO-level, recorded for completeness.

## Explicit confirmations (verified, not assumed)

- **No change to authorization surface.** `git diff HEAD` and `git status --porcelain` contain neither `app/api/admin/route.ts` nor `firestore.rules`. Confirmed. No route or rule was touched.
- **No new endpoint / no rate-limit gap introduced.** `/sync_stok` remains a Telegram admin command routed through `handleCommand.js` / `handleKonfirmasiCallback.js`; not modified by this diff.
- **No hardcoded secrets.** The diff adds no credential. `stockMovements.js`/`syncStokDuaArah.js` read only `process.env` via `lib/firebase.js` / `lib/sheets/client.js` (startup validation already present there: `firebase.js:20-41`, `client.js:20-24`).
- **Tests are offline, no real credentials, no network.**
  - `test/syncStokReplay.test.js:15-23` and `test/syncStokMovementIdempotensi.test.js:9-17` set `FIREBASE_PROJECT_ID/CLIENT_EMAIL` to fake `demo-*`/`demo@example.com` and generate an ephemeral in-memory RSA key with `crypto.generateKeyPairSync` (never written to disk, never a real credential).
  - `test/helpers/mockFirestore.js:160-176` stubs `firebase-admin/app` and `firebase-admin/firestore`, and deletes `lib/firebase` from `require.cache` so the real admin SDK/ADC is never initialized → no Firestore network.
  - `test/syncStokReplay.test.js:63-77` and `test/syncStokMovementIdempotensi.test.js:31-42` stub `lib/sheets/client` in `require.cache`; telegram is stubbed (`:27-42`, `:20-27`). No `fetch`/`axios`/`https` call occurs in these suites. Confirmed offline.
- **No sensitive logging of PII/secrets in the new code.** The only new log is MINOR-1 above; it carries no timestamped tokens, no admin identity, no auth headers.
- **Idempotency does not weaken access control.** `id_movement` only changes the write from `.add()` to `.doc(id).set()`; it cannot write outside the `stock_movements` collection (Firestore id validation), and `created_by`/`requested_by`/`confirmed_by` are still derived server-side in `stockMovements.js:41-52`.

## Residual risks / notes (not defects of this diff)

- `konfirmasiSyncStok` does not itself re-verify the caller's role; it trusts `telegramUserId` (session-keyed) and the `idPemilik` passed by the callback handler. Draft `owner_user_id` is written (`syncStokDuaArah.js:216`) but is not enforced inside this module. This is pre-existing and outside this change set; noted so it is not mistaken for a new regression.
- The append-then-marker window for PRODUK_BARU leaves a residual risk of a duplicate Sheets row on crash (documented at `syncStokDuaArah.js:568-571`); the movement itself is guaranteed unique by the deterministic id. Data-integrity (duplicate row), not security.
